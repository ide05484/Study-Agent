# 공부법 DB와 코치 지식 설계 (로드맵 2.1)

- 날짜: 2026-11-18
- 상태: 사용자 승인(2026-11-18), 구현 계획 전
- 관련: [로드맵 2.1](../plans/2026-10-27-roadmap.md), [docs/study-methods](../../study-methods/README.md), [코치 톤](../../coach/coach-tone.md), [채팅 연결 History 피드백 1번](../../../History/2026-10-30-채팅-연결.md)

## 배경과 목적

사용자가 조사 문서 "보건직 공무원 과목별 공부법"(2027 보건직 기준, 과목별 공부법 + 시간관리 + 멘탈관리, 항목마다 [확인]/[추정]/[미확인]과 출처)을 정리했다. 이 문서로 `docs/study-methods`의 초안(✏️ 표시가 남은 상태)을 채우고, 그 내용을 DB에 넣는다.

목적은 **점수가 떨어지거나 힘들어할 때 코치가 근거 있게 코칭하는 바탕**을 만드는 것이다. 지금 코치 질문 답변(`chat/reply.ts`의 `question`)에는 공부법이 전혀 들어가지 않는다. 공부 설정의 "과목별 공부법" 탭은 "기본 공부법은 준비 중이에요"와 비활성 메모 칸만 있다.

## 정한 것 (사용자 결정, 2026-11-18)

| 질문 | 결정 |
|---|---|
| 화면에 보여 줄 형태 | **정리본**. 과목마다 "과목 특징 / 단계별 공부법 / 고민별 처방". [확인]/[추정] 표시와 출처는 화면에 보이지 않고 문서에만 남긴다 |
| 강조 | 중요한 부분은 굵게만이 아니라 **형광펜**(기존 `marker`)으로도 표시 |
| 내 메모 칸 | **만들지 않는다**. 수험생이 메모를 쓰며 앉아 있지 않는다 |
| 대신 | 채팅에서 "오늘 이렇게 공부하니 잘 된 것 같아" 같은 말을 알아듣고 **그 사람에게 잘 맞은 방법으로 저장**한다 |
| 저장 방식 | **바로 저장**. 확인 질문 없이 저장하고, 코치가 적어 뒀다고 알린다. 잘못 저장된 것은 탭에서 지운다 |
| 멘탈관리 | 공부법 탭에 **멘탈관리 아코디언**을 더한다. 과목 4개와 멘탈관리 모두 접고 펼친다 |
| 멘탈관리 문구 | 의지를 북돋우는 말. 상대는 **ENTJ 성향**: 감정적인 응원도 좋지만 **방향과 현실을 분명히 하고, 가능성과 해결책을 제시**하는 것이 꼭 필요하다 |
| ENTJ 대응 범위 | 모든 사용자에게 같은 문구·지침으로 적용한다. 실제로는 한 사람에게 맞춤으로 쓰는 앱이다. 사용자별 성향 설정은 만들지 않는다 |
| 시간관리 | 화면에 보이지 않는다. 코치가 질문에 답할 때만 쓴다 |
| DB에 넣는 방법 | **문서 → 마이그레이션 생성 스크립트**(아래 "방법") |

## 방법 (검토한 안과 고른 것)

| 안 | 내용 | 장단점 |
|---|---|---|
| **A. 문서 → 마이그레이션 생성 (선택)** | 스크립트가 `docs/study-methods`의 내용 파일을 읽어 공부법 테이블을 통째로 바꾸는 새 마이그레이션 SQL을 만든다 | `main`에 들어가면 기존 배포 흐름(GitHub Actions `db push`)이 개발·운영에 자동 반영한다. 문서를 고칠 때마다 마이그레이션이 하나씩 쌓인다(배포된 파일은 안 고친다는 규칙과는 맞음) |
| B. 문서 → DB 동기화 스크립트 | 비밀 키로 DB에 직접 덮어쓴다 | 마이그레이션이 쌓이지 않지만 개발·운영에 각각 손으로 돌려야 해 운영 반영을 잊기 쉽고, 매번 클라우드 작업 승인이 필요하다 |
| C. DB 없이 TS 상수(로드맵 원래 안) | 문서를 상수로 만들어 화면과 `chat`이 함께 쓴다 | 가장 단순하지만 사용자가 원한 "DB에 저장"이 아니고, 내용만 바꿔도 프론트·함수를 다시 배포해야 한다 |

사용자는 A를 골랐다.

## 목표와 범위

**목표**
- 공부 설정 "과목별 공부법" 탭에 과목 4개의 정리본과 멘탈관리가 보인다.
- 코치가 질문에 답할 때, 질문한 과목의 공부법과 그 사람에게 잘 맞은 방법, 필요하면 멘탈·시간관리 지식을 근거로 답한다.
- 채팅에서 잘 맞은 방법을 말하면 저장되고 탭과 코치 답변에 반영된다.

**하지 않는 것**
- 메모 입력 칸(비활성 `TextArea`는 지운다)
- 잘 맞은 방법을 화면에서 직접 쓰거나 고치기(채팅으로만 넣고, 화면에서는 지우기만)
- "이렇게 하니 안 되더라" 같은 안 맞은 방법 저장
- 공부법 내용을 앱 안에서 고치기(원본은 문서, 반영은 마이그레이션)
- 예/아니오 칩(피드백 4번), 답변 속도 개선(피드백 2번)은 따로 한다

**실패로 볼 것** (동작은 해도 안 되는 것)
- [추정]·[미확인] 내용을 화면이나 코치 답변이 사실처럼 단정한다.
- 공부법 원문을 질문마다 통째로 프롬프트에 넣어 답변이 지금(20~30초)보다 눈에 띄게 느려진다.
- 공부법이 앱의 계획 규칙과 어긋나는 말을 한다(아래 "내용 작성 규칙").
- 형광펜이 한 과목에 여기저기 칠해져 강조가 의미를 잃는다.

## 1. 문서 (원본)

### 파일 구성

`docs/study-methods/` 안의 파일을 다음처럼 나눈다.

| 파일 | 역할 | DB `topic` | 화면 |
|---|---|---|---|
| `README.md` | 쓰는 규칙, 형식, 반영 방법 (DB에 안 들어감) | – | – |
| `korean.md`, `english.md`, `public-health.md`, `health-admin.md` | 과목 정리본 | `korean`, `english`, `public_health`, `health_admin` | 보임 |
| `mental.md` (새 파일) | 멘탈관리 | `mental` | 보임 |
| `time.md` (새 파일) | 시간관리 + 공통 원칙(회독, 기출 우선, 오답 관리, 학습 단계) | `time` | 안 보임(코치만) |
| `research/2026-11-보건직-과목별-공부법.md` (저장해 둠) | 사용자가 2026-11-18 대화에 첨부한 조사 문서 원문 그대로. [확인]/[추정]/[미확인]과 출처의 근거 | – | – |

- 지금 `README.md`의 "학습 단계 (공통)", "공통 원칙"은 `time.md`로 옮긴다. README에는 "공부법을 제안하는 순서", "주의"처럼 문서를 쓰고 쓰는 규칙만 남긴다.
- 과목 파일의 `(초안)`, `✏️` 표시는 모두 없앤다.

### 내용 파일 형식 (스크립트가 읽는 형식)

```markdown
# 공중보건

## 과목 특징
- 같은 주제가 해마다 되풀이된다. ==반복 출제 주제는 무실점==이 목표예요.
- **역학은 매년 출제**돼요. …

## 단계별 공부법
| 단계 | 공부법 |
|---|---|
| 기본 | … |

## 고민별 처방
| 고민 | 처방 |
|---|---|
| 점수가 정체됨 | … |
```

- `# 제목` 한 줄, 그 아래 `## 소제목` 섹션들. 섹션 본문은 **목록(`- `)** 이거나 **두 칸 표**(첫 줄은 머리글) 중 하나만.
- 글 안 꾸밈은 `**굵게**`와 `==형광펜==` 두 가지만. 링크, 그림, 중첩 목록, 문단 글은 쓰지 않는다(스크립트가 오류로 멈춘다).
- 형광펜은 **파일마다 최대 3곳**. 스크립트가 넘으면 오류로 멈춘다.
- 섹션 순서가 화면 순서다.

### 내용 작성 규칙

- 출처는 조사 문서. [확인]은 그대로 단정해도 되고, [추정]은 "~하는 편이 안전해요", "~로 보여요"처럼 단정하지 않는 말로 쓴다. [미확인]은 넣지 않는다.
- 2027 시험 제도(과목당 25문항, 110분, 한국사 대체)는 [확인]이지만 근거가 보도뿐인 항목(110분 유지 등)은 "보도 기준"으로 적는다.
- 날짜는 "11월~1월" 같은 달 대신 "시험 7~5개월 전"처럼 시험일 기준으로 쓴다. 시험일은 사용자마다 `profiles.exam_date`로 다르다.
- 특정 강사·학원·교재를 추천하지 않는다(README "주의"). 합격수기는 "합격자 사례"로만 쓴다.
- **앱 계획과 맞춘다.** 조사 문서의 "초반에는 부담 과목 하나에 집중"은 앱 계획(매일 모든 교재를 나눠 배정)과 어긋난다. "매일 모든 과목을 계획대로 조금씩 하고, 약한 과목 하나에 추가 시간을 쓴다"로 바꿔 쓴다.
- 과목 정리본은 기존 세 섹션(과목 특징, 단계별 공부법, 고민별 처방)을 유지한다. "하루 공부 예시"는 조사 문서에 근거가 있는 과목(영어: 단어 50개 + 하프 15분 등)만 남기고 나머지는 뺀다.
- 말투는 해요체([코치 톤](../../coach/coach-tone.md)).

### 멘탈관리 내용 (힘들 때 말하는 방식)

- 근거는 조사 문서 Part 3(점수는 3~4회 평균으로 보기, 수면 규칙성, 주 1일 휴식, 초반 과속 금지, 걱정 적기, 아는 느낌 경계, 2주 이상 이어지면 도움 구하기)와 Part 2의 장기화 패턴.
- 화면과 문서 본문에 "ENTJ"라는 말은 쓰지 않는다. 이 방식은 성향과 상관없이 모든 사용자에게 같은 문구로 적용한다(사용자 결정). 이유는 coach-tone.md에만 적는다.
- 섹션은 상황별로 나눈다. 예: `점수가 떨어졌을 때`, `공부가 손에 안 잡힐 때`, `불안하고 비교될 때`, `몸과 리듬`, `시험 직전`.
- 섹션마다 목록 2~4개를 **현실 → 방향 → 가능성 → 바로 할 해결책** 순서로 쓴다. 위로로 시작하지 않는다. 감정적인 응원은 섹션 끝에 짧게 한 번까지.
  - 예(점수가 떨어졌을 때): "한 회차 점수는 실력이 아니라 오차예요. 3~4회 평균으로 봐요." → "오답을 개념 부족·실수·시간 부족으로 나눠요." → "합격자 사례에서도 전공 35점이 두 달 뒤 80점대로 올랐어요." → "이번 주는 가장 많은 원인 하나만 고쳐요."
- 합격 가능성 단정, 다른 수험생과 비교, 건강을 해치는 공부량 권유는 하지 않는다(코치 톤 "하지 않을 것").

### 코치 톤 문서

`coach-tone.md`에 "힘들 때 말하는 방식" 항목을 더하고, 이 방식을 정한 이유(사용자가 ENTJ 성향이라 방향·현실·해결책이 꼭 필요하다는 요청, 2026-11-18)를 함께 적는다. 모든 사용자에게 같게 적용한다. 적용 범위: 멘탈관리 탭 문구와, 코치가 **점수 하락·지침·불안**에 답할 때. 평소 기록 답변은 지금 말투(공감 → 칭찬 → 제안 → 질문)를 유지한다. 해당 상황에서는 순서를 "현실 확인 → 방향 → 가능성(기록 근거) → 바로 할 행동 하나 → 짧은 응원"으로 바꾼다.

## 2. DB

### 공부법 내용 `public.study_methods`

| 칸 | 타입 | 규칙 |
|---|---|---|
| `topic` | `text` | `korean`, `english`, `public_health`, `health_admin`, `mental`, `time` 중 하나(check) |
| `position` | `smallint` | 문서 안 섹션 순서(1부터) |
| `heading` | `text` | 섹션 소제목 |
| `kind` | `text` | `list` 또는 `pairs`(check) |
| `items` | `jsonb` | `list`: 문자열 배열. `pairs`: `{ "label": …, "text": … }` 배열. 문자열 안에 `**`·`==` 꾸밈을 그대로 둔다 |

- 기본 키 `(topic, position)`.
- 모든 사용자가 같은 내용을 본다. RLS를 켜고 `authenticated`에 **읽기 정책만** 둔다. `anon` 권한 없음. 쓰기는 마이그레이션(관리자 권한)으로만 한다.
- `topic`을 `public.subject` enum으로 하지 않는 이유: `mental`·`time`이 함께 들어가야 한다. 과목 값 4개는 `subject` enum과 같은 문자열을 쓴다.

### 잘 맞은 방법 `public.study_tips`

| 칸 | 타입 | 규칙 |
|---|---|---|
| `id` | `uuid` | 기본 키 |
| `user_id` | `uuid` | `auth.users` 참조, 지우면 함께 지움 |
| `subject` | `public.subject` | null 가능(과목이 없는 방법, 예: "아침에 단어부터 하니 집중이 잘 됐다") |
| `content` | `text` | 1~200자. 코치가 한 문장으로 다듬은 방법 |
| `source_message_id` | `uuid` | `chat_messages` 참조, 메시지가 지워지면 null |
| `created_at` | `timestamptz` | |

- RLS: 다른 테이블처럼 `user_id = auth.uid()`.
- 인덱스 `(user_id, subject, created_at desc)`.
- 개수 상한은 두지 않는다. 코치에는 과목별 최근 5개만 넘긴다(진행자 판단).

### 마이그레이션

1. **스키마**: `npx supabase migration new study_methods`로 만든 파일에 두 테이블, RLS, 인덱스. 손으로 쓴다.
2. **내용**: 스크립트가 만든다(아래). 스키마 마이그레이션보다 뒤 타임스탬프.

### 내용 마이그레이션 생성 스크립트

- `Backend/package.json`에 `"methods:migration": "tsx scripts/study-methods-migration.ts"`.
- 하는 일: 내용 파일 6개를 읽고 형식을 검사한 뒤, `supabase/migrations/<UTC 타임스탬프>_study_methods_content.sql`을 새로 쓴다. 내용은 `delete from public.study_methods;` + 모든 섹션 `insert`. 문자열은 SQL 이스케이프(작은따옴표 두 번) 또는 달러 인용으로 안전하게 넣는다.
- 형식 오류(알 수 없는 줄, 형광펜 3곳 초과, 빈 섹션, 파일 없음)는 파일·줄 번호와 함께 멈추고 아무 파일도 쓰지 않는다.
- 파싱은 순수 모듈로 나눠 테스트한다(OpenAI·Supabase를 부르지 않는 파일만 테스트하는 기존 규칙). 테스트를 `npm test`에 포함할 위치는 진행자가 정한다.
- 내용을 고친 뒤 흐름: 문서 수정 → `npm run methods:migration` → 생성된 SQL 확인·커밋 → `db push`(개발, 사용자 요청 시) → `main` 병합 시 운영 자동 반영. README에 적는다.
- 이미 배포된 내용 마이그레이션은 고치지 않는다. 문서를 다시 고치면 새 파일을 만든다.

## 3. chat 함수

### 분석 (GPT 1번째 호출, 호출 수는 그대로)

`ANALYSIS_SCHEMA`에 두 칸을 더한다. strict 스키마라 둘 다 `required`에 넣고 null을 허용한다.

- `study_tip: { subject: subject | null, content: string } | null` — 사용자가 **자기에게 잘 맞았던 공부 방식**을 말했을 때만. "오늘 기출 풀고 바로 백지 복기하니까 잘 외워졌어" → `{ public_health 또는 null, "기출을 풀고 바로 백지 복기하기" }`. 단순한 기분("오늘 공부 잘 됐다")이나 분량 보고만 있는 말은 null. 방법이 있어야 한다.
- `knowledge: ("mental" | "time")[]` — 답변에 필요한 지식. 점수 하락·지침·불안·슬럼프 → `mental`, 시간 배분·하루 루틴·시험 당일 운영·직장 병행 → `time`. 둘 다 또는 빈 배열.

`analysis.ts`가 검증한다: `content`는 공백을 다듬고 1~200자가 아니면 버린다. 팁의 `subject`가 null이면 메시지의 `subject`를 쓴다. `knowledge`는 알려진 값만 남기고 중복을 지운다.

intent는 늘리지 않는다. 잘 맞은 방법은 학습 기록 `entries`처럼 **intent와 상관없이** 저장한다("보건행정 15강까지 했고, 비교표로 정리하니 잘 들어왔어"는 기록과 팁을 함께 저장).

### 저장

- `index.ts`: 사용자 메시지를 넣은 뒤, `study_tip`이 있으면 `study_tips`에 넣는다(`db.ts`에 함수). 같은 사용자·같은 과목(null 포함)에 공백을 다듬은 내용이 똑같은 팁이 이미 있으면 넣지 않고, 답변에서도 "적어 뒀다"고 하지 않는다(진행자 판단). 넣기가 실패하면 로그만 남기고 답변은 계속한다(답변에서 "적어 뒀다"고 말하지 않음).
- 하루 상한을 넘은 메시지, 분석 실패 메시지는 저장하지 않는다(지금 규칙 그대로).

### 답변 (GPT 2번째 호출)

답변 지침에 넣는 지식은 **필요한 것만**:

| 조건 | 넣는 것 |
|---|---|
| intent `question`이고 `subject`가 있음 | 그 과목의 `study_methods` 섹션 전부 + 그 과목 `study_tips` 최근 5개 |
| intent `question`이고 `subject`가 없음 | 과목 공통(`subject` null) `study_tips` 최근 5개 |
| `knowledge`에 `mental` | `mental` 섹션 전부 + 힘들 때 말하는 방식 지침(아래) |
| `knowledge`에 `time` | `time` 섹션 전부 |
| intent `study_log`, `schedule` | 지식은 넣지 않는다(지금처럼 짧은 답). 단 `knowledge`가 있으면 위 규칙대로 넣는다 |

- 지식은 `study_methods`에서 한 번의 조회(`topic in (...)`)로 읽고, `loadCoachContext`와 동시에 부른다. 읽기 실패는 지식 없이 답한다(대체 답변으로 가지 않는다).
- 지식을 프롬프트 글로 바꾸는 함수는 순수 모듈(`chat/knowledge.ts` 등)에 두고 테스트한다. `**`·`==` 꾸밈은 지운다.
- 지침에 더할 문장:
  - 지식이 있을 때: "아래 공부법은 참고 자료다. 질문에 맞는 것 1~2개만 고르고, 통째로 옮기지 않는다. 출처나 강사 이름을 말하지 않는다."
  - 잘 맞은 방법이 있을 때: "이 수험생에게 잘 맞았던 방법이다. 맞으면 먼저 이걸 살려서 제안한다."
  - `mental`일 때: coach-tone.md의 "힘들 때 말하는 방식"을 요약한 지침(`_shared/coach.ts`에 상수로).
  - 이번 메시지로 팁을 저장했을 때: "이번 메시지의 방법을 '<과목> 공부법'(과목이 없으면 '공부법')에 적어 뒀다고 한 문장으로 알려 준다."
- 대체 답변(`fallbackReply`)도 팁을 저장했으면 "잘 맞은 방법도 공부법에 적어 뒀어요."를 붙인다.
- 정해진 문구로 답하는 의도(usage, book_add, study_time만)에서 팁을 저장했으면 정해진 문구 뒤에 같은 한 문장을 붙인다.
- `USAGE_GUIDE`에 한 줄: `- 잘 맞은 공부법을 말해 주면 공부 설정의 과목별 공부법에 모아 둬요. 예) 기출 풀고 바로 백지 복기하니까 잘 외워졌어`

## 4. 화면 (공부 설정 "과목별 공부법" 탭)

```
과목별 공부법
─────────────────────────────
▸ 국어
▸ 영어
▾ 공중보건
  과목 특징
  · 같은 주제가 해마다 되풀이돼요. [반복 출제 주제는 무실점]이 목표예요.
  · 역학은 매년 출제돼요 …
  단계별 공부법
    기본   기본서로 전체 구조 …
    기출   …
  고민별 처방
    점수가 정체됨   …
  내게 잘 맞은 방법
  · 기출을 풀고 바로 백지 복기하기   11/18  [✕]
▸ 보건행정
▸ 과목 공통        ← 과목 없는 잘 맞은 방법이 있을 때만
▸ 멘탈관리
  점수가 떨어졌을 때
  · …
```

- 아코디언 순서: 국어, 영어, 공중보건, 보건행정, (과목 공통), 멘탈관리. 기존 `Disclosure`를 쓴다. 처음엔 모두 닫혀 있다.
- 섹션 소제목은 `text-sm font-semibold`, `list`는 점 목록, `pairs`는 줄마다 `label`(굵게) + `text`(아래 또는 옆). 폰 폭(360px)에서 표가 좁아지지 않게 표 대신 정의 목록 형태로 그린다.
- 꾸밈: `**…**` → 굵게, `==…==` → 형광펜(`marker`). 이 두 가지 외에는 글 그대로(HTML로 해석하지 않음).
- **내게 잘 맞은 방법**: 과목 아코디언 맨 아래. 최신순, 줄마다 내용 + 날짜(`text-xs text-muted`) + 지우기(`IconButton`, `useConfirm`으로 확인). 없으면 `채팅에서 "이렇게 하니 잘 됐어"라고 말해 주면 여기에 모아 둘게요.`(`text-sm text-muted`).
- 과목 공통 아코디언은 내용 섹션 없이 "내게 잘 맞은 방법" 목록만. 하나도 없으면 아코디언을 그리지 않는다.
- 불러오는 중 `Notice`("불러오는 중…"), 실패 시 오류 `Notice`(코치 톤 오류 문구). 탭을 열 때 한 번 읽는다.
- 메모 `TextArea`와 "준비 중" 안내는 지운다.
- 시간관리(`time`)는 읽지 않는다(조회에서 뺀다).

### 디자인 규칙 예외

DESIGN.md의 형광펜 규칙("한 화면에 여러 군데 남발하지 않는다")에 예외를 적는다: 과목별 공부법은 문서마다 형광펜 최대 3곳, 한 번에 한 아코디언씩 읽으므로 허용한다. 컴포넌트는 기존 토큰만 쓴다.

## 5. Frontend 구조

- `interfaces/studyMethod.ts`: `StudyMethodTopic`, `StudyMethodSection`, `StudyTip`(DB 칸 그대로 snake_case). `gen:types` 뒤 `database.ts` 타입과 맞춘다.
- `api/studyMethods.ts`: 공부법 섹션 조회(`time` 제외), 내 팁 조회, 팁 지우기.
- `hooks/useStudyMethods.ts`: 위를 감싼 상태.
- `libs/`에 꾸밈 파서(문자열 → 글·굵게·형광펜 조각). 프론트 테스트 도구가 아직 없으므로 `/ui` 카탈로그에 예시를 둔다.
- `components/settings/`에 공부법 섹션·팁 목록 컴포넌트. `SettingsPage`는 탭 패널만 바꾼다.

## 확인 방법

- `npm test`: 문서 파서(형식 오류, 형광펜 상한, 이스케이프), 분석 검증(`study_tip`·`knowledge`), 지식 → 프롬프트 글 변환.
- 생성된 SQL을 개발 DB에 `db push`(사용자 승인) 후 `authenticated`로 `study_methods` 읽기 가능·쓰기 불가, `study_tips` 다른 사용자 차단 확인.
- 채팅(개발): "공중보건 점수가 계속 떨어져서 힘들어" → 공중보건 공부법 + 멘탈(ENTJ 순서), "기출 풀고 바로 백지 복기하니까 잘 외워졌어" → 저장되고 탭에 보임, "하루 시간 배분을 어떻게 해야 해?" → 시간관리 근거, "오늘 공부 잘 됐다" → 저장 안 됨.
- 화면: 폰 폭에서 아코디언·형광펜·팁 지우기, 라이트·다크.
