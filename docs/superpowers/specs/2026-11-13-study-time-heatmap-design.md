# 순공시간과 공부 잔디, 밤 재분배 설계 (묶음 C)

- 날짜: 2026-11-13
- 상태: 설계 정리(구현 계획 전)
- 관련: [로드맵](../plans/2026-10-27-roadmap.md), [채팅 연결 계획](../plans/2026-10-27-chat-connection.md) 요구사항 C, [묶음 B 설계](2026-11-12-today-plan-sheet-design.md)

## 배경

묶음 B를 마친 뒤 사용자가 두 가지를 요청했다.

1. 계획 재분배는 하루가 지날 때마다 스케줄러로 한다. 체크하거나 채팅으로 "~했음"을 보낼 때마다 재분배되어 분량이 바뀌면 부담스럽다. 공부 설정을 바꾸면 지금처럼 바로 재분배한다.
2. 채팅으로 "나 오늘 순공 N시간 N분이야"를 보내면 반영한다.

예상 소요 시간(오늘 분량이 몇 시간 걸릴지)도 검토했지만 **만들지 않는다**. 사용자: "오늘 4시간밖에 못 하는데 분량이 예상 6시간이면 숨이 턱턱 막힐 것 같다." 그래서 교재별 시간 값도 받지 않는다.

이 설계는 두 부분이다.

- **C1. 밤 재분배**: 방향과 결정만 적는다. 구현은 아침 알림 단계에서 한다(같은 서버 스케줄 작업).
- **C2. 순공시간과 공부 잔디**: 채팅으로 받은 순공시간을 저장하고, 대시보드 공부 잔디를 순공시간으로 칠한다.

## 정한 것 (사용자 결정)

| 질문 | 결정 |
|---|---|
| 재분배 시점 | 매일 새벽 1~4시 사이(사용자 시간대) 서버가 사용자마다 이월 재분배를 하고, 아침 알림은 그 결과로 보낸다 |
| 앱을 열 때 이월(묶음 B) | 예비로 남긴다. 밤에 이미 했으면 지난 미진행 분량이 없어 아무것도 하지 않는다 |
| 체크·채팅 보고 | 진도만 바꾸고 재분배하지 않는다. 앞서 공부한 분량은 다음 날 계획에서 줄어든다 |
| 공부 설정 변경 | 지금처럼 바로 재분배한다 |
| 예상 소요 시간 | 만들지 않는다 |
| 순공시간 보고 | 채팅으로만. 저장 방식은 진행자가 정한다 |
| 잔디 기준 | 순공시간을 보낸 날은 순공시간으로 칸을 채운다 |
| 순공시간을 안 보낸 날 | 칸은 비우고 가운데 주황 점 하나(진행률과 상관없이 한 가지 색). 녹색 등 새 색은 쓰지 않는다 |
| 순공시간 단계 | 2시간 미만 1단계 · 2~4시간 2단계 · 4~6시간 3단계 · 6시간 이상 4단계 |

## C1. 밤 재분배

- 매일 사용자 시간대(`profiles.timezone`)로 새벽 1~4시 사이에 서버가 사용자마다 `plan-generator`와 같은 재분배를 한다. 지난 날짜의 `pending`은 `skipped`가 되고 남은 분량이 남은 날로 나뉜다(묶음 B의 `replace_daily_tasks` 그대로).
- 아침 알림(`daily-briefing`, `profiles.notify_time`)은 그 뒤에 오늘 `daily_tasks`를 읽어 보낸다.
- 앱을 열 때 이월(`useCarryOver`)은 그대로 둔다. 밤 작업이 실패한 날만 대신한다.
- 체크(`set_task_done`)와 채팅 완료 보고는 진도만 바꾼다. 계획 밖 공부(다른 교재, 앞서 나간 분량)도 진도만 바꾸고, 다음 계획은 밤 재분배에서 맞춰진다.
- 공부 설정 변경(교재 추가·삭제, 진도·목표 회독·목표일 수정, 시험일 변경)은 지금처럼 바로 `plan-generator`를 부른다.
- 구현은 아침 알림 단계에서 한다. 정할 것: 서버가 사용자 토큰 없이 사용자마다 재분배하는 방법(지금 `plan-generator`는 로그인한 사용자 토큰으로만 돈다), 스케줄(pg_cron)과 시간대별 실행 시각, 실패 재시도.

## C2. 순공시간

### 저장

새 테이블 `public.study_time`:

| 칸 | 타입 | 규칙 |
|---|---|---|
| `user_id` | `uuid` | `auth.users` 참조, 지우면 함께 지움 |
| `study_date` | `date` | 공부한 날(사용자 시간대) |
| `minutes` | `integer` | 1 이상 1080(18시간) 이하 |
| `created_at`, `updated_at` | `timestamptz` | |

- 기본 키 `(user_id, study_date)`. 하루에 한 줄이다.
- RLS: 다른 테이블과 같이 `user_id = auth.uid()`.
- `study_logs`에 칸을 더하지 않는다. `study_logs`는 "어느 교재 몇 회차"를 적는 줄이라 하루 합계와 성격이 다르고, 하루에 줄이 여러 개일 때 합계를 어디에 둘지 애매하다.

저장은 DB 함수 `public.record_study_time(p_date date, p_minutes integer, p_add boolean) returns integer`(저장된 그날 합계)로 한다.

- `p_add = false`: 그날 합계를 `p_minutes`로 바꾼다(없으면 넣는다).
- `p_add = true`: 그날 합계에 더한다(없으면 넣는다).
- 결과가 1~1080분을 벗어나면 오류(SQLSTATE `22023`)로 저장하지 않는다.
- `security invoker`, `set search_path = ''`, `authenticated`에만 실행 권한. 한 문장(`insert … on conflict … do update`)으로 더하기가 겹쳐도 맞게 한다.

### 채팅으로 보고

`chat` 함수의 의도에 "순공시간 보고"를 더한다(채팅 연결 계획 Task 3~7에서 의도 분류를 만들 때 함께).

- "오늘 순공 3시간 20분", "순공 200분" → 그날 합계로 저장(`p_add = false`). 다시 보내면 바꾼다.
- "1시간 더 했어", "추가로 40분" → 더한다(`p_add = true`).
- 날짜: 말이 없으면 오늘, "어제"는 어제. **사용자 시간대로 새벽 0~4시에 "오늘"이라고 보내면 전날**로 본다(밤늦게 공부를 마치고 보내는 경우). 그 외 날짜 표현은 학습 기록 보고와 같은 규칙을 따른다.
- 범위를 벗어나거나 시간을 알아들을 수 없으면 저장하지 않고 다시 묻는다.
- 답장은 저장한 합계를 짧게 알려 주고 수고를 알아준다([coach-tone](../../coach/coach-tone.md)). 목표나 다른 날과 비교해 재촉하지 않는다. 예: `오늘 순공 3시간 20분으로 적어 뒀어요. 오늘도 수고 많으셨어요.`
- 순공시간 보고는 진도·계획을 바꾸지 않는다. 같은 메시지에 완료 보고가 같이 있으면("보건행정 15강까지 했고 순공 4시간") 둘 다 처리한다.

## C2. 공부 잔디

지금 잔디는 그날 계획 대비 달성률로 칸을 채운다(DESIGN.md "구현 메모"). 아래로 바꾼다.

| 그날 | 칸 |
|---|---|
| 순공시간 있음 | 칸을 주황으로 채운다: 120분 미만 `heat-1`, 120~239분 `heat-2`, 240~359분 `heat-3`, 360분 이상 `heat-4` |
| 순공시간 없음, 진행한 분량(`done`·`partial`)이나 `study_logs`가 있음 | `heat-0` 칸 가운데 주황 점 하나(`bg-accent`, 지름은 칸의 약 40%) |
| 아무것도 없음 | `heat-0` |

- 새 색 토큰은 만들지 않는다. 점은 `accent`를 쓴다.
- 칸마다 날짜와 내용을 `title`·`aria-label`로 단다: `11월 13일 · 순공 3시간 20분`, `11월 13일 · 순공시간 안 적음, 분량 75%`, `11월 13일 · 순공시간 안 적음, 공부 기록 있음`, `11월 13일 · 기록 없음`. 색이나 점만으로 알리지 않는다.
- 범례: 지금의 `적음 ~ 많음`(순공시간 단계) 아래에 `● 순공시간 안 적은 날` 한 줄을 더한다.
- 표시 기간은 그대로 최근 20주(`HEATMAP_WEEKS`).
- **연속 공부**: 위 표에서 `heat-0` 빈칸이 아닌 날(순공시간, 진행한 분량, 공부 기록 중 하나라도 있는 날)을 공부한 날로 센다. 지금은 `study_logs`만 센다. 오늘이 아직 비어 있으면 어제까지 세는 규칙은 그대로.
- 순공시간 단계 경계(120·240·360분)는 `libs/` 상수 하나로 두고 DESIGN.md에 적는다.

## 바뀌는 곳

- Backend
  - 새 마이그레이션: `study_time` 테이블·RLS, `record_study_time`
  - `chat` 함수: 순공시간 보고 의도(채팅 연결 단계)
- Frontend
  - `api/study.ts`: 기간의 순공시간 조회
  - `hooks/useDashboard.ts`: 잔디 칸 계산(순공시간 → 단계, 없으면 점), 연속 공부
  - `components/dashboard/StudyHeatmap.tsx`: 점, `title`·`aria-label`, 범례 한 줄
  - `pages/UiCatalogPage.tsx`: 잔디 예시에 점 칸
- 문서
  - DESIGN.md: 잔디 설명·단계·범례, 연속 공부 기준
  - SERVICE_FLOW.md: 5장에 순공시간 보고, "chat 의도별 처리" 표에 한 줄, "구현 전 결정할 것"의 "분량↔시간 환산"에 "예상 소요 시간은 만들지 않기로 함(2026-11-13)"
  - 채팅 연결 계획: 요구사항 C(채팅 보고는 진도만, 재분배는 밤), 순공시간 의도

## 순서

- C2는 채팅 연결(Task 3~7)과 함께 구현한다. 보고 경로가 채팅뿐이라, 잔디만 먼저 만들면 점만 찍힌다.
- 테이블과 잔디를 먼저 만들고 채팅 의도를 나중에 붙여도 동작은 맞다(순공시간이 없으면 지금 기준과 비슷하게 점으로 보인다). 구현 계획에서 순서를 정한다.
- C1은 아침 알림 단계에서 구현한다.

## 확인 방법

- 개발 DB(`db query --linked`): `record_study_time`의 바꾸기·더하기·범위 밖 오류·다른 사용자 차단
- Frontend 순수 계산(잔디 단계, 연속 공부)은 테스트 도구가 없으므로 `/ui` 예시와 Mock 데이터로 확인
- 채팅: "오늘 순공 3시간 20분", "1시간 더 했어", 새벽 1시의 "오늘 순공 5시간"(전날로 저장), "순공 30시간"(다시 물음)
