# 채팅으로 교재 추가 설계

- 날짜: 2026-11-23
- 상태: 사용자 승인(2026-11-23), 구현 계획 전
- 브랜치: `feature/study_knowledge`에서 이어서 한다. 이 작업이 끝나면 push한다(사용자 결정). 하루 첫 메시지 개선(피드백 1번)은 다음 브랜치로 넘긴다.
- 관련: [SERVICE_FLOW 6장 교재 추가](../../../SERVICE_FLOW.md#6-교재-추가), [코치 톤](../../coach/coach-tone.md), [채팅 연결 History 피드백 4번(예/아니오 칩)](../../../History/2026-10-30-채팅-연결.md), [공부법 History 피드백 표](../../../History/2026-11-18-공부법-채우기.md)

## 배경과 목적

사용자가 채팅에서 "책 추가할래"라고 보냈더니 교재가 추가되지 않았다(2026-11-23 피드백 2번). 지금 `chat`은 `book_add` 의도에 "공부 설정에서 추가하세요"라는 정해진 문구(`BOOK_ADD_PENDING`)만 돌려준다. SERVICE_FLOW 6장은 원래 "채팅으로 입력받아 `books`에 저장하고, 저장한 내용을 다시 확인해 준다"를 목표로 적어 두었다.

목적은 **채팅 한두 마디로 교재를 등록하고, 시험일까지 분량이 바로 다시 나뉘게 하는 것**이다. 공부 설정 화면까지 가지 않아도 된다.

## 정한 것 (사용자 결정, 2026-11-23)

| 질문 | 결정 |
|---|---|
| 저장 시점 | **확인 후 저장**. 정보가 다 모이면 요약을 보여 주고 확인을 받은 뒤 저장한다 |
| 확인 방법 | 코치 메시지 아래 **응 / 아니 칩**을 누른다(글로 "응"을 치지 않아도 되게) |
| 칩을 누르면 | GPT를 거치지 않고 서버가 바로 처리한다(제안 1 승인) |
| 기본값 | 목표 회독을 말하지 않으면 1회독, 진도는 처음부터(1회독 0). 회독별 목표일·하루 최소 분량은 채팅에서 받지 않고 공부 설정에서만 정한다(제안 2 승인) |
| 빠진 정보 | 과목·교재명·단위·총량 중 빠진 것은 글로 다시 묻고, 다음 메시지에서 받아 둔 내용을 이어 받는다(제안 3 승인) |
| "아니"를 누르면 | **고치기**. "어떤 걸 고칠까요?"라고 묻고, 답한 부분만 바꿔 다시 확인 칩을 띄운다. 칩이 떠 있을 때 "아니, 3회독이야"처럼 글로 답해도 같게 고쳐진다 |
| 칩 대신 글로 확답하면 | **칩과 똑같이 처리**. 정해 둔 짧은 긍정어("응", "네" 등)는 응 칩, 짧은 부정어("아니", "아니요" 등)는 아니 칩과 같다. 서버가 단어 목록으로 판단하고 GPT를 거치지 않는다. 내용이 붙은 말("아니, 3회독이야")은 분석으로 넘겨 고친다 |
| 받아 둔 내용을 두는 곳 | **A1. 코치 메시지에 붙인다**(아래 "방법") |
| 저장 뒤 재분배 | **B1. 나누는 코드를 공용 모듈로 빼서 `chat`과 `plan-generator`가 같이 쓴다** |

## 방법 (검토한 안과 고른 것)

### 받아 둔 교재 정보를 두는 곳

| 안 | 내용 | 장단점 |
|---|---|---|
| **A1. 코치 메시지에 붙이기 (선택)** | `chat_messages`에 메시지에 달린 동작(`action`) 칸을 더한다. 받아 둔 교재와 지금 단계(되묻는 중/확인 중/고치는 중)를 담는다 | 새로고침해도 남고, 칩을 그 메시지 아래에 그리면 된다. 나중에 "오늘은 마무리할까요?" 같은 다른 예/아니오 칩도 같은 칸을 쓸 수 있다 |
| A2. 별도 테이블 | 사용자마다 진행 중인 교재 추가 한 줄 | 단순하지만 칩과 메시지를 따로 이어야 하고, 다른 칩에 다시 쓰지 못한다 |
| A3. 화면에만 | 칩을 누를 때 받아 둔 내용을 통째로 보낸다 | DB를 안 바꾸지만 새로고침하면 사라지고, 화면이 보낸 값을 서버가 믿어야 한다 |

### 저장 뒤 계획 재분배

| 안 | 내용 | 장단점 |
|---|---|---|
| **B1. 공용 모듈 (선택)** | `plan-generator`의 본문을 `_shared/replan.ts`로 옮기고 `chat`과 `plan-generator`가 같이 부른다 | 저장과 재분배가 한 요청에서 끝나고, 답변에 오늘 분량을 넣을 수 있다. `plan-generator` 동작은 그대로다 |
| B2. 화면이 `plan-generator` 호출 | 공부 설정과 같은 방식 | 화면 쪽 호출이 실패하면 교재만 있고 계획이 없는 채로 남는다. 답변에 결과를 넣지 못한다 |
| B3. `chat`이 `plan-generator`를 HTTP로 호출 | 함수에서 함수 부르기 | 한 번 더 거치고 콜드 스타트가 겹친다. B1보다 나은 점이 없다 |

## 목표, 하지 않을 것, 실패로 보는 것

**목표**
- 채팅으로 과목·교재명·단위·총량(+목표 회독)을 받아 확인 칩으로 저장하고, 바로 시험일까지 다시 나눈다.
- 칩 처리와 되묻기·확인 문구는 정해진 문구로 하여 GPT 호출을 늘리지 않는다. 메시지당 GPT 호출은 지금처럼 분석 1번 + 답변 1번까지이고, 이 흐름의 답변은 모두 정해진 문구다(분석 1번만).
- 칩이 달린 메시지 구조(`action`)는 다른 예/아니오 질문에도 쓸 수 있게 만든다. 이번에 쓰는 곳은 교재 추가뿐이다.

**하지 않을 것**
- 채팅으로 회독별 목표일, 하루 최소 분량, 시작 진도(이미 몇 회 봤는지)를 받기. 공부 설정에서 한다.
- 채팅으로 기존 교재를 고치거나 지우기.
- 교재 추가 외의 예/아니오 칩(예: "오늘은 마무리할까요?").
- 하루 첫 메시지·아침 알림(피드백 1번, 다음 브랜치).

**실패로 보는 것 (동작하더라도)**
- 확인 없이 교재가 저장된다.
- 칩 한 번에 교재가 두 권 생긴다.
- 교재는 저장됐는데 계획이 다시 나뉘지 않은 채로 사용자가 모른다.
- 교재와 상관없는 메시지가 받아 둔 교재를 엉뚱하게 고친다.
- 되묻기·칩 때문에 GPT 호출이 늘어난다.

코치: 이렇게 추가할까요?

나:   (응)            ← 사용자 말풍선 "응"

정보가 처음부터 다 있으면("영어 단어장 Day 60 추가해줘") 되묻지 않고 바로 확인 칩을 띄운다.

### 단계

받아 둔 교재는 **오늘 채팅방의 마지막 메시지가 `action`이 있는 코치 메시지일 때만** 살아 있다. 사용자가 다른 메시지를 보내 그 뒤로 대화가 이어지면 받아 둔 교재는 버려진다. 날이 바뀌면(채팅방이 바뀌면) 버려진다.

| 지금 마지막 코치 메시지 | 사용자 입력 | 처리 | 다음 코치 메시지 |
|---|---|---|---|
| (없음 또는 `action` 없음) | 교재 추가 의도(`book_add`) 글 | 분석 결과의 교재 정보로 초안을 만든다 | 빠진 게 있으면 **되묻기**(`ask`), 다 있으면 **확인**(`confirm`, 칩) |
| `ask` 또는 `edit` | 글 | 분석에 받아 둔 초안을 함께 넘긴다. 분석이 이 초안을 채우거나 고치는 말로 보면 합친다 | 빠진 게 있으면 `ask`, 다 있으면 `confirm` |
| `confirm` | **응 칩** | GPT 없이 초안을 다시 검증하고 저장 → 재분배 | 저장 결과(정해진 문구, `action` 없음) |
| `confirm` | **아니 칩** | GPT 없이 | **고치기**(`edit`, 같은 초안, 칩 없음) "어떤 걸 고칠까요? 예) 3회독이야, 30회분이야" |
| `confirm` | 정해 둔 긍정어 글("응", "네 추가해줘" 등) | 응 칩과 같다(분석 없음) | 저장 결과 |
| `confirm` | 정해 둔 부정어 글("아니", "아니요" 등) | 아니 칩과 같다(분석 없음) | `edit` |
| `confirm` | 그 밖의 글 | `ask`/`edit`와 같다. "아니, 3회독이야" → 고쳐서 다시 `confirm` | `ask` 또는 `confirm` |
| `ask`/`confirm`/`edit` | 교재와 상관없는 글 | 초안을 버리고 평소처럼 처리한다(학습 기록, 질문 등) | 평소 답변(`action` 없음) |

받아 둔 초안이 있을 때 "이 말이 초안을 채우거나 고치는 말인지"는 분석이 정한다. 분석 지침에 초안과 빠진 항목을 함께 넣고, 그 말이 초안에 대한 답이면 의도를 `book_add`로, 아니면 원래 의도로 고르게 한다.

## 데이터

### `chat_messages.action` (새 마이그레이션)

```sql
alter table public.chat_messages add column action jsonb;
```

- null이면 평범한 메시지. 지금 있는 행은 모두 null.
- jsonb가 객체인지만 DB에서 막고(`check (action is null or jsonb_typeof(action) = 'object')`), 모양은 함수 코드가 검증한다.
- RLS는 기존 "own rows"(for all)로 충분하다. 사용자가 자기 `action`을 직접 바꿀 수는 있지만, 응 칩을 처리할 때 서버가 초안을 다시 검증하고, 사용자는 원래 `books`에 직접 넣을 권한이 있으므로 새 권한이 생기지 않는다.
- 한 번 쓴 `action`은 고치지 않는다(상태를 메시지마다 새로 남긴다). 그래서 지난 칩이 눌렸는지는 바로 다음 사용자 말풍선("응"/"아니")으로 보인다.

`action` 모양 (교재 추가):

```ts
interface BookAddAction {
  kind: "book_add";
  step: "ask" | "confirm" | "edit";
  draft: {
    subject: Subject | null;
    title: string | null;        // 앞뒤 공백 뺀 1~20자
    unit: BookUnit | null;
    total_units: number | null;  // 1~1000 정수 (채팅 전용 상한)
    target_rounds: number;       // 1~10, 기본 1
  };
}
```

Frontend `interfaces/chat.ts`의 `ChatMessage`에 `action: ChatAction | null`을 더한다. 메시지 조회(`fetchChatMessages`, 함수의 `MESSAGE_COLUMNS`)도 `action`을 함께 읽는다.

### `books`에 넣는 값

`subject`, `title`, `unit`, `total_units`, `target_rounds`는 초안에서, 나머지는 기본값: `current_round` 1, `current_unit` 0, `daily_amount` null, `round_targets` `{}`. 기존 DB 제약(제목 1~20자, 목표 회독 1~10 등)이 마지막으로 막는다.

## 요청·응답

`ChatRequest`는 글 또는 칩 선택 둘 중 하나다.

```ts
type ChatRequest =
  | { content: string }
  | { choice: { message_id: string; answer: "yes" | "no" } };
```

- 칩 요청도 사용자 메시지로 남는다(`content`는 "응"/"아니"). 칩 요청 자체는 상한을 확인하지 않지만, 남은 메시지는 이후 글 메시지의 상한 계산에 들어간다("설계자가 정한 것").
- 서버는 `message_id`가 **오늘 채팅방의 마지막 메시지이고, `action.step`이 `confirm`인 코치 메시지**일 때만 처리한다. 아니면(이미 눌렸거나 지난 메시지) 아무것도 저장하지 않고 "이 확인은 끝났어요. 추가할 교재를 다시 말해 주세요." 같은 정해진 문구로 답한다.
- `ChatResponse`에 `planChanged: boolean`을 더한다. 교재를 저장하고 재분배했으면 true이고, 화면은 `logged`처럼 오늘의 분량을 다시 불러온다.

## 서버(`chat`) 변경

- **분석** (`analysis.ts`, `llm.ts`)
  - 스키마에 `book` 항목을 더한다. 필드는 `subject`·`title`·`unit`·`total_units`·`target_rounds`이고, 말하지 않은 것은 null이다. 교재 추가나 초안 답이 아니면 `book` 자체가 null이다.
  - 받아 둔 초안이 있으면 분석 지침 끝에 초안과 빠진 항목을 넣는다. 분석 입력은 지금처럼 이번 메시지 하나다.
  - 지침에는 SERVICE_FLOW 6.1 규칙을 넣는다.
    - 교재명은 20자 안으로 줄인다. 연도·출판사·강사 이름은 뺀다.
    - "모의고사 몇 개"처럼 모호한 분량은 null로 둔다.
    - 쪽 수는 단위로 쓰지 않는다.
    - 인강 세트는 회차로 센다.
  - 검증은 `parseAnalysis`가 한다. 범위를 벗어난 값은 null로 버린다. 20자를 넘는 제목도 null로 버려 다시 묻는다.
- **초안 순수 모듈** (`chat/bookDraft.ts`, 새 파일, 테스트 대상)
  - 초안 합치기: 새로 들어온 null 아닌 값이 덮어쓴다.
  - 빠진 항목 찾기.
  - 되묻기·확인·고치기·저장 결과·끝난 확인 문구 만들기. 단위 표기는 `_shared/units.ts`의 `withUnit`을 쓴다.
  - `action`·요청 모양 검증.
  - 되묻기 문구는 빠진 항목을 한 메시지에 모아 묻는다. 예: 과목이 빠지면 "어느 과목 교재인가요?", 단위·총량이 빠지면 "어떤 단위로 모두 몇 개인지 알려 주세요. 예) 20회분, 12챕터, Day 30".
  - 문구 말투는 [코치 톤](../../coach/coach-tone.md)을 따른다. 상황별 패턴 표의 "교재 추가: 입력 내용 확인 + 계획 재분배 결과 안내"에 맞춘다.
- **DB** (`chat/db.ts`)
  - 오늘 채팅방의 마지막 메시지(`action` 포함) 읽기.
  - 교재 넣기.
  - `insertMessage`에 `action` 인자 추가.
- **확답 글 판단** (`bookDraft.ts`)
  - 마지막 메시지가 `confirm`일 때만 본다. 앞뒤 공백과 문장부호(`.!~?` 등)를 뺀 글이 목록의 말과 정확히 같으면 칩으로 본다.
  - 긍정어 예: 응, 어, 네, 넵, 예, 그래, 좋아, 맞아, ㅇㅇ, ㅇㅋ, 오케이, 추가해줘, 추가해 줘, 네 추가해줘, 응 추가해줘.
  - 부정어 예: 아니, 아니요, 아니야, 아뇨, 노, ㄴㄴ.
  - 최종 목록은 만드는 사람이 정한다. 기준은 "확인에 대한 짧은 답으로만 읽히는 말"이다. 애매하면 목록에 넣지 않고 분석으로 넘긴다.
  - 이렇게 처리한 글은 하루 메시지 상한 계산에서 칩 요청처럼 다룬다. 상한을 따지지 않는다.
- **흐름** (`chat/index.ts`)
  - 칩 요청과 확답 글은 분석 없이 처리한다.
  - 글 요청은 받아 둔 초안을 분석에 넘긴다. 분석 의도가 `book_add`이면 초안을 합쳐 `ask`/`confirm`을 정해진 문구로 답한다.
  - 학습 기록·순공시간·잘 맞은 방법 저장은 지금처럼 의도와 상관없이 한다. 이번에 잘 맞은 방법을 저장했으면 `fixed()`처럼 끝에 알린다.
  - `BOOK_ADD_PENDING`은 지운다.
- **재분배** (`_shared/replan.ts`, 새 파일)
  - `plan-generator/index.ts`의 본문을 `replan(sb)`로 옮긴다. `replan(sb)`는 `{ generated, days, skipped? }`를 돌려주고, 실패하면 Error를 던진다.
  - `plan-generator`는 이것을 불러 지금과 같은 응답을 돌려준다. 동작은 바뀌지 않아야 한다.
  - `chat`은 교재를 넣은 뒤 이것을 부른다.
- **저장 결과 답변**
  - 성공: "국어 「봉투모의고사」 20회, 3회독을 추가했어요." 다음 문단에 재분배 결과를 쓴다.
  - 새 교재의 오늘 분량이 있으면 "오늘은 1–2회예요."(`rangeLabel`)를 덧붙인다. 없으면 "시험 전날까지 분량을 다시 나눴어요."까지만 쓴다.
  - 시험일이 없거나 지났으면(`skipped`) "시험일을 정하면 분량을 나눠 드려요. 메뉴의 '공부 설정 변경'에서 정할 수 있어요."로 답한다.
  - 재분배가 실패하면 교재는 남긴다. 응답에 `replanFailed: true`를 담고, 화면은 이것을 받으면 `regeneratePlan()`을 한 번 부른다(B2를 안전망으로만 쓴다). 저장한 교재를 지우고 다시 누르게 하는 안(둘 다 되거나 둘 다 안 되게)도 검토했지만, 실패가 드물고 다시 나누면 사용자가 모르게 해결되므로 이 방식을 골랐다(사용자 결정, 2026-11-23). 답변 문구는 교재를 추가했다고만 하고 실패를 따로 알리지 않는다. 화면의 재시도도 실패하면 공부 설정에서 저장하면 다시 나뉜다.
- **사용법**: `USAGE_GUIDE`에 "새 교재도 채팅으로 추가할 수 있어요. 예) 국어 봉투모의고사 20회분 추가해줘" 줄을 더한다.

### 두 번 눌림 막기

- 화면은 보내는 동안(`sending`) 칩을 막는다.
- 서버는 "그 확인 메시지가 오늘 마지막 메시지인지"를 확인한다. 응 칩 처리에서는 사용자 메시지 "응"을 먼저 저장하므로, 같은 칩으로 두 번째 요청이 오면 마지막 메시지가 바뀌어 거절된다.
- 두 요청이 거의 같은 순간에 들어오면 둘 다 통과할 수 있다. 이 틈을 어디까지 막을지는 만드는 사람이 정한다(아래 "만드는 사람에게 맡기는 것").

## 화면 변경

- `ChatPage`의 코치 말풍선 아래에 칩 줄을 그린다. 그리는 조건은 셋 다 맞을 때다.
  - 오늘 채팅방이다(읽기 전용 아님).

  - 모양은 칩과 같다: `min-h-11 rounded-xl border px-3`, `border-line`.
  - 44px 터치 영역을 지킨다.
  - 보내는 동안 `disabled`로 둔다.
  - 접근성 이름은 "응"/"아니"다.
- `useChat`에 `choose(messageId, answer)`를 더한다. 보내는 동안 "응"/"아니" 임시 말풍선과 답변 대기 말풍선을 보이는 방식은 `send`와 같다.

## 설계자가 정한 것 (사용자 검토 대상)

빌더 검토에서 나온 질문 중 만드는 쪽에서 정할 수 있는 것은 아래처럼 정했다.

- **같은 이름의 교재가 이미 있을 때**: 막지 않는다. 같은 과목에 같은 제목이 있으면 확인 문구에 "같은 이름의 교재가 이미 있어요." 한 줄을 더하고, 그래도 응을 누르면 저장한다. 개정판이나 2회차 구매처럼 일부러 같은 이름을 쓸 수 있고, `books`에 제목 유니크 제약도 없다. 받아 둔 교재 목록(`loadProfileAndBooks`)으로 판단하므로 조회는 늘지 않는다.
- **총량 상한**: 채팅에서는 `total_units`를 1~1000만 받는다. 넘으면 null로 버려 다시 묻는다. 분석이 숫자를 잘못 읽어 "20000회" 같은 값이 계획에 들어가는 것을 막는 장치다. 공부 설정 화면과 DB에는 상한이 없고, 그대로 둔다.
- **하루 메시지 상한(100개)과 칩**: 칩 요청은 GPT를 부르지 않으므로 상한을 확인하지 않고 처리한다. 사용자 메시지("응"/"아니")는 남기므로 이후 글 메시지의 상한 계산에는 들어간다. 상한이 찬 날에도 이미 띄운 확인을 끝낼 수 있게 하려는 것이다.
- **교재 추가와 학습 기록이 한 메시지에 같이 있을 때**("영어 단어장 Day 60 추가했고 오늘 Day 3 했어"): 학습 기록은 지금처럼 먼저 저장한다. 아직 등록 전인 교재의 기록은 교재를 모르므로(`book_id` null) 기록만 남고 진도는 바뀌지 않는다(지금 동작과 같다). 답변은 교재 추가 흐름의 정해진 문구를 따르고, 기록을 저장했으면 `logged`를 true로 둔다. 교재를 저장한 뒤 그 기록을 진도로 옮기지는 않는다. 필요하면 공부 설정에서 진도를 고친다.

## 만드는 사람에게 맡기는 것

- 분석 스키마의 `book` 항목 이름과 지침 문장.
- 정해진 문구의 정확한 문장. 위 예와 코치 톤을 따른다.
- 칩 요청 검증 실패 응답의 상태 코드. 형식이 틀리면 400, 끝난 확인이면 정해진 문구 200을 생각하고 있다.
- 거의 동시 두 요청으로 생기는 중복 저장 틈을 더 막을지. 예: 사용자 메시지 저장 뒤 마지막 메시지를 다시 확인하기. 막지 못한 중복은 공부 설정에서 지울 수 있다.
