# 작업 기록 (History)

개발·계획·설계 작업을 할 때마다 **무엇을 어떻게 했는지, 어떤 상황을 고려해 어떻게 풀었는지, 무엇을 제안해 무엇이 결정됐는지**를 남긴다. 코드와 git 기록만으로는 남지 않는 판단의 이유를 남기는 것이 목적이다.

## 언제 쓰나

- 계획을 세우거나 바꿀 때 (로드맵, 단계별 상세 계획)
- 계획의 Task 하나를 끝냈을 때 (리뷰 결과 포함)
- 설계·디자인·데이터 구조를 정했을 때
- 클라우드 작업(DB 반영, 함수 배포, 비밀 값 등록, 외부 서비스 설정)을 했을 때
- 버그나 막힌 문제를 해결했을 때

## 쓰는 법

- 파일 이름: `YYYY-MM-DD-작업-이름.md` (예: `2026-10-27-개발-계획-수립.md`)
- 작업 단위 하나에 파일 하나. 같은 작업이 이어지면 같은 파일 아래에 덧붙인다(날짜를 소제목으로).
- 계획을 Task 단위로 실행할 때는 Task마다 파일을 만들지 않고, 그 단계 파일에 Task별 소제목으로 쌓는다.
- 서브에이전트가 구현한 Task도 진행을 맡은 메인 세션이 기록한다. 서브에이전트 보고와 리뷰 지적, 그 처리 결과를 함께 적는다.
- 사실만 적는다. 하지 않은 확인은 "안 함" 또는 "보류"로 적고 이유를 남긴다.
- API 키, 비밀번호, 토큰, 개인 정보는 적지 않는다.
- 새 파일을 만들면 아래 목록에 한 줄을 추가한다.

## 템플릿

```markdown
# <작업 이름>

- 날짜: YYYY-MM-DD
- 단계: <로드맵 단계 / Task>
- 관련: <계획 문서, 커밋, PR 링크>

## 요청

사용자가 무엇을 요청했는지 한두 문장.

## 한 일

무엇을 어떤 순서로 했는지. 만든·바꾼 파일과 확인 결과(빌드, 테스트, 수동 확인).

## 고려한 상황과 해결

### 1. <상황 한 줄>

- 상황: 무엇이 문제였거나 무엇을 고려해야 했는지
- 선택지: 검토한 방법들 (있으면)
- 해결: 무엇을 골랐고 왜
- 남긴 규칙·프로세스: 이 일로 생긴 규칙이나 절차 (있으면)

## 제안과 결정

| 제안 | 결정 | 비고 |
|---|---|---|
| Claude가 제안한 것 | 승인 / 수정 / 거절 / 보류 / 답 없음 | 사용자가 정한 내용 |

## 남은 일

- 다음에 할 일, 보류한 확인, 아직 정하지 않은 것
```
