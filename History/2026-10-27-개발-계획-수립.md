## 요청

화면 골격이 끝났으니 기능별 순서를 정해 개발하고 싶다. 순서는 1. 채팅 연결, 2. 공부 데이터 DB 채우기, 2.1 공부법 채우기, 3. 대시보드 화면 연결. 디자인 시스템을 적용하는 방법도 알려 달라.

이어서 받은 수정 요청:
- 로그인은 처음부터 카카오로 구현한다. 카카오 API 키는 사용자가 나중에 받아서 넣는다.
- 공부 데이터 단계에서 넣을 것: 가진 교재와 분량, 지금까지 공부한 범위, 모의고사 점수, 실제 시험 점수(지방직 2회), D-Day까지 목표 공부량(모든 교재 1회독 + 기본서 N회독).
- 실행은 Subagent-driven으로 하고, Task 3~6만 Native로 할 수 있는지 검토해 달라.
- 지금부터 작업 기록을 History 폴더에 남긴다.

## 고려한 상황과 해결

### 1. 채팅에 필요한 기반이 아직 없음

- 상황: 채팅은 로그인한 사용자(RLS), DB 테이블, OpenAI 키가 있어야 동작한다. 개발용 Supabase 프로젝트에는 아직 테이블이 없고 로그인도 없다.
- 해결: 순서 앞에 "0. 기반"을 두고, 1단계 계획의 Task 1(DB 반영·비밀 값·타입)과 Task 2(로그인)로 넣었다.

### 2. 로그인 방식과 카카오 키가 없는 기간

- 상황: 처음에는 카카오 앱 설정·심사에 시간이 걸린다고 보고 개발용 이메일 로그인을 제안했다. 사용자는 처음부터 카카오로 가고 싶어 했고, 키는 나중에 받는다.
- 선택지: (a) 키가 올 때까지 1단계를 멈춘다. (b) 화면에 개발용 이메일 로그인을 임시로 둔다. (c) 카카오 로그인 코드는 지금 만들고, 키가 필요한 확인만 미룬다.
- 해결: (c). 앱 화면에는 카카오 로그인만 둔다. 키 없이도 `chat` 함수를 확인할 수 있도록, 대시보드에서 만든 **검증용 테스트 계정**으로 Auth API에서 토큰을 받아 curl로 호출한다. 이 계정은 화면에서 쓰지 않는다.
- 남긴 규칙·프로세스: 키가 필요한 단계는 🔑로 표시하고, 키가 없으면 그 단계만 건너뛴 뒤 History에 "보류"로 남기고 다음 Task로 간다. 운영 프로젝트는 Email provider를 끈다(DEPLOY.md에 반영 예정).

### 3. 카카오 이메일 동의항목 제약

- 상황: Supabase 문서에 따르면 카카오의 `account_email` 동의항목은 비즈 앱으로 등록해야 받을 수 있다.
- 해결: 이메일은 받지 않고 `profile_nickname`, `profile_image`만 쓰며, Supabase Kakao provider에서 "Allow users without an email"을 켠다. 카카오 화면에 KOE205(설정하지 않은 동의항목)가 나오면 요청 scope를 직접 지정하는 대응을 계획에 넣었다.
- 남은 고려: 카카오톡 메시지 발송(`talk_message` 동의, 카카오 토큰 보관)은 알림 단계에서 추가 동의를 받는 방식으로 붙인다.

### 4. 아직 정하지 않은 기능을 채팅이 받게 되는 문제

- 상황: 사용자가 "알바 4시간"처럼 일정을 말하면 분량을 다시 나눠야 하지만, 이월 방식과 시간 환산이 정해지지 않았다(SERVICE_FLOW "구현 전 결정할 것"). 채팅으로 교재 추가도 2단계 일이다.
- 해결: 1단계에서는 의도만 분류한다. 일정에는 "재배분했다"고 말하지 않게 답변 지침을 주고 테스트로 고정했다. 교재 추가는 공부 설정 화면으로 안내하는 고정 문구를 쓴다.

### 5. LLM 출력을 그대로 믿을 수 없음

- 상황: LLM이 없는 과목, 틀린 교재 id, 뒤집힌 쪽수, 푼 문제보다 많은 오답 수를 낼 수 있다. 같은 과목에 교재가 여러 권이면 엉뚱한 교재 진도를 올릴 수 있다.
- 해결: OpenAI 구조화 출력(json_schema strict)으로 형식을 고정하고, `parseAnalysis`가 결정적 규칙으로 다시 검증한다. 교재를 특정할 수 없으면 진도는 건드리지 않고 기록만 남긴다. 진도 계산과 오늘 분량 상태 변경은 LLM이 아닌 코드가 한다.

### 6. 같은 메시지를 다시 보냈을 때 기록이 두 번 쌓이는 문제

- 해결: 분석에 실패하면 아무것도 저장하지 않고 오류를 돌려준다. 진도는 `max`로만 올라가서 같은 기록을 다시 보내도 더 늘지 않는다. `study_logs` 행 중복은 이번 단계에서는 허용했다.

### 7. 날짜 경계 (UTC와 한국 시간)

- 상황: `study_logs.study_date`의 DB 기본값은 `current_date`(UTC)라서, 한국 시간 0~9시에 남긴 기록이 전날로 저장될 수 있다.
- 해결: 기록 날짜는 항상 `profiles.timezone` 기준으로 계산해 직접 넣고, 자정 직후 사례를 테스트로 고정했다.

### 8. 테스트 도구가 없음

- 상황: 프로젝트에 테스트 프레임워크가 없다. 이전에 `deno check`를 돌렸을 때 `deno.lock`이 생겨 지운 적이 있다.
- 해결: Edge Function의 순수 로직(OpenAI·Supabase를 import하지 않는 파일)을 분리하고 `deno test --no-lock`으로 테스트한다. npm `deno` 패키지를 devDependency로 둬서 따로 설치하지 않아도 된다. 프론트엔드 테스트(Vitest)는 계산이 많은 3단계에서 들인다.

### 9. 클라우드를 바꾸는 작업

- 해결: `db push`, `functions deploy`, `secrets set`, 대시보드 설정 단계에 ☁️를 붙여 사용자 승인 후에만 실행하도록 계획에 적었다(CLAUDE.md 규칙과 같음).

### 10. 디자인 시스템을 언제, 어떻게 적용할지

- 상황: 색상 토큰(`@theme`)과 기준 문서(DESIGN.md)는 이미 있지만, 버튼·입력 필드는 `classes.ts`의 문자열 묶음뿐이다. 2·3단계에서 입력 폼과 대시보드 영역이 늘어난다.
- 해결: 채팅 연결 다음, 공부 데이터 전에 "1.5 디자인 시스템 정리" 단계를 넣었다. 자체 컴포넌트(`Button`, `TextField` 등)로 바꾸고, 개발 모드 전용 `/ui` 카탈로그 화면으로 확인한다.
- 선택지로 본 것: shadcn/ui는 기본 모양(둥근 카드, 그림자)이 "플래너 괘선" 스타일과 맞지 않아 지금은 쓰지 않는다. 접근성 처리가 어려운 부품(대화상자, 토스트)이 필요할 때 그 부품만 가져온다. Storybook은 카탈로그 화면으로 대신한다.

### 11. 회독 목표가 스키마에 없음

- 상황: 사용자가 말한 목표("교재 1회독 + 기본서 N회독")를 지금 스키마는 표현하지 못한다. `books`는 교재당 1회독(`current_page` → `total_pages`)만 담는다.
- 해결: 2단계에서 새 마이그레이션으로 목표 회독 수와 현재 회독을 추가하고 `plan-generator`가 회독까지 분배하게 한다. 1단계 Task 1에서 초기 스키마를 `db push`하므로, 그 뒤에는 초기 스키마를 고치지 않고 새 마이그레이션을 쓴다(CLAUDE.md 규칙). 실제 시험 점수는 `mock_exams`에서 모의고사와 구분하는 값을 두기로 했다.

### 12. 실행 방식 섞기 (Subagent-driven + 일부 Native)

- 상황: 사용자는 Subagent-driven을 원하고, Task 3~6만 Native로 할 수 있는지 물었다.
- 검토: 가능하다. Subagent-driven에서는 진행을 맡은 메인 세션이 Task마다 구현자를 정하므로 일부를 직접 구현할 수 있다. Task 3~6은 같은 타입(`Analysis`, `BookRef`, `CoachContext`)을 이어 쓰고 Task 6에 배포가 있어서, 한 흐름에서 구현하고 끝에 묶어서 리뷰받는 편이 낫다. Task 1도 대부분 클라우드 작업과 사용자 작업이라 바로 승인을 받아야 해서 Native가 맞다.
- 해결(제안): Task 1 Native, Task 2 Subagent + 리뷰, Task 3~6 Native + 묶음 리뷰 1회, Task 7 Subagent + 리뷰, 마지막에 전체 브랜치 리뷰. 서브에이전트 리뷰는 Task별 커밋 diff를 보므로 Task마다 커밋해야 한다.

### 13. 작업 기록 방식

- 상황: 사용자가 단계별 작업 기록, 특히 고려한 상황과 해결 과정을 남기고 싶어 했다.
- 해결: 저장소 루트에 `History/`를 만들고, README에 언제 쓰는지·쓰는 법·템플릿·목록을 두었다. CLAUDE.md에 규칙을 연결해 다음 세션에서도 지키게 했다. 서브에이전트가 구현한 Task도 메인 세션이 리뷰 결과까지 묶어 기록한다.
